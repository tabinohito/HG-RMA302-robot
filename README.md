# HG-RMA302：ジョイスティック／タンク操作とWT61 Yaw補正

Linux PCに接続したF310から、ST-Link仮想COM経由で2枚のB-G431B-ESC1を操作します。ジョイスティックモードと左右独立のタンクモードをXboxロゴボタンで切り替えられます。ESCが電流を調整して速度を保ち、WT61のYaw・角速度で直進と旋回を補正します。

現在の設定は**車輪の目標速度8〜100 RPM、スティック全倒し30 RPM、各輪のq軸電流上限2 A、始動電流1 A、加速FF上限0.3 A**です。2 Aはバッテリー入力電流の指定ではありません。車輪を浮かせた試験用で、接地・実負荷での走行確認はまだです。B・通信断による停止はPWMを切る動作で、保持ブレーキではありません。

## Pico電源・パネルの統合

`embedded/` にPico電源コントローラとESP32表示パネルを取り込みました。[設定・配線・LED・ビルド手順](embedded/README.md) を参照してください。`power.enabled=true` のとき、Pythonから電圧・電流・Statusを取得し、走行状態をLEDへ反映します。約5 VのUSB給電だけなら `USB_ONLY` で待機し、両輪の駆動電圧が入って中立操作を確認するまで始動しません。

このモードでは **B＝両ESC停止＋SSR OFF・停止保持、Start＝中立で保持解除、物理ボタン＝電源再投入** です。StartでSSRはONになりません。Ctrl-CもSSRを切ります。Python／USB通信断が750 ms続くとPico側でSSRを切って停止を保持します。`--log` に `power` の測定値とStatusを追加しました。`uv run hg-cart power --config config.local.json` で、SSRやLEDを変更せずStatusだけ読めます。

## ジョイスティックモード・Yaw補正（2026-11-08）

`config.local.json` はジョイスティックモードで起動し、WT61補正も有効です。現在のローカル設定は全体上限・スティック全倒しとも100 RPMです。配布JSONのスティック上限は30 RPMなので、機体別設定を使ってください。

| 操作 | ジョイスティックモード |
| --- | --- |
| 左スティック縦 | 両輪の前進・後退 |
| 左スティック横 | 走行中の曲がり。**±0.2以内は横入力ゼロ**。外側を残りの傾きに比例して使用 |
| 右スティック横 | 旋回。左縦が中立ならその場旋回、前後入力中なら旋回を加算 |
| 右スティック縦 | 使用しない |
| Xboxロゴ／Guideボタン | タンク↔ジョイスティックを1回ずつ切替。押しっぱなしでは連続切替しない |
| 十字キー・B・Start | 従来と共通。BはSSR OFF、Startは停止保持だけ解除 |

切替時はPWM停止を指示し、両スティックと十字キーを中立へ戻すまで再始動しません。起動時にXboxボタンを押している場合も、一度離してから押してください。F310/F710などGuide非搭載機種では `drive.control_mode` で選択できます。左横だけではその場旋回しません。後退中の横入力も車体が向く右／左を指定します。

設定は `drive.control_mode` (`joystick` / `tank`)、`steering_deadzone`（横軸、初期0.2）、`deadzone`（縦軸、従来0.12）、`joystick_turn_ratio`（右横全倒し時の各輪速度／スティック上限、初期0.5）です。上限を超える組合せは左右を同じ比率で縮小します。ESCの下限8 RPMは残るため、非ゼロ指令は最低8 RPMへ制限します。横軸不感帯をなくす設定や、8 RPM未満の連続駆動を行う機能ではありません。

テープLEDは**先頭24灯が走行状態、末尾6灯がモード**です。末尾が水色ならタンク、橙ならジョイスティック。非常停止・異常では全灯が赤になり、モード表示より優先します。Picoの新ファームウェアには `cap` に `drive_modes=1` が必要で、旧版は新Python起動時に拒否します。ESP32・ESCの再書き込みは不要です。

### WT61のYaw制御

タンク・ジョイスティック・十字キーのすべてで補正します。直進時はその区間の開始方向を保持し、意図した曲がり・旋回時は目標Yaw角速度と実測角速度の差で左右速度を調整します。中立、B、モード切替、電源待機で古い方向目標を破棄します。停止中に元の方向へ向き直る動作はしません。

Yaw補正は両輪の始動完了を待ってから行います。左右速度差による既存の補正はIMU有効時には使わず、共通の始動待ち・加速平滑化を残します。補正は最大±8 RPMで、加速上限も超えません。停止中の車輪の始動、指令方向の反転、8 RPM未満の駆動は補正から行いません。上限・下限付近では補正できる幅が減ります。

WT61は115200 baud、USB固定接続パスで読み取ります。このCH340にはUSB固有シリアルがないため、ハブの同じ差込口を使ってください。生加速度のZが約+0.97 g、Roll/Pitchが小さいことを確認し、Z上向き・`yaw_sign=-1`（車体右旋回を正）として設定しました。機体を手で右へ回したときに、モニターの `yaw_rate_dps` が正になる取り付けが前提です。

```bash
# ESC・SSRを操作せず、姿勢・角速度・校正状態を表示
uv run hg-cart imu --config config.local.json --seconds 10

# 通常の走行。IMUデータと補正値も同じログへ記録
uv run hg-cart drive --config config.local.json --live --log
```

起動後は機体を約1秒静止させ、`IMU_CALIBRATING` の終了を待ちます。静止条件（約1 g・小さい角速度・ばらつき）が満たされるまで始動しません。受信遅延・古いデータ・チェックサム不正の連続・角度の不自然な飛びを有効な観測には使いません。通常の小さな通信欠損は次の正しいフレームで再同期します。角度または角速度が150 ms以上古ければ走行を止め、電源統合有効時はSSRもOFFにします。Roll/Pitchが±35°を超える取り付け・姿勢は停止条件です。

| `imu`設定 | 初期値・用途 |
| --- | --- |
| `enabled` | ローカルtrue、配布例false。falseにするとIMUなしの従来制御 |
| `port` / `serial` | 固定USB接続パス、または固有シリアル。指定機器だけを開く |
| `baudrate` / `yaw_sign` | 115200 / -1。取り付け変更時は符号を確認 |
| `timeout_s` / `calibration_s` | 0.15秒 / 1秒 |
| `heading_kp` | 1.5：方向誤差1°あたりの目標旋回速度（°/s） |
| `rate_kp` | 0.12：角速度誤差1°/sあたりの片輪補正（RPM） |
| `max_yaw_rate_dps` | 90：左右が全体速度上限で逆回転する場合の目標角速度。実際には加速後の指令割合で縮小 |
| `max_correction_rpm` | 8：片輪の補正上限 |
| `correction_slew_rpm_s` | 20：補正変化率。最終加速はdrive側の上限も守る |

`--log` の `input` に横軸とモードボタン、`output.control_mode` に選択モード、`imu` に姿勢・角速度・校正・受信経過時間・目標角速度・補正RPM・補正後目標を追加します。実際の送信値は従来の `wheels.*.last_sent_mrpm` を参照します。

受信形式は[メーカーのWT61対応SDK説明](https://wit-motion.gitbook.io/witmotion-sdk/wit-standard-protocol/sdk/python_sdk-quick-start)の11バイト形式です。[WT61仕様書](https://m.media-amazon.com/images/I/81Zlk6ZohiL.pdf)にあるとおりYawには積分誤差があり、絶対方位を長時間保証するものではありません。初期ゲインは控えめに設定しています。受信・停止・模擬外乱への補正は検証していますが、接地状態での蛇行量・負荷ごとのゲイン調整は未確認です。

## 起動と操作

```bash
uv sync
# 入力だけを表示。ESCは接続しない
uv run hg-cart gamepad

# 左右の目標速度を表示。モーターは動かない
uv run hg-cart drive --config config.local.json

# 実際にモーターを操作
uv run hg-cart drive --config config.local.json --live
```

走行プログラムと入力モニターは同時に実行しないでください。ゲームパッドを排他取得し、シリアルも排他オープンします。終了はCtrl-C、時間を区切るには `--seconds 120` を付けます。

`no valid response to 'cartcap'` は、起動時のESC仕様問い合わせに有効な応答がなかったことを示します。エラーには左右、USB固有番号、今回の問い合わせ中の受信バイト数、完全な行数、未完了行の長さを表示し、`--log` にも残します。`received_bytes=0` は無受信、値がある場合は末尾の応答／未完了データで切り分けられます。この段階では走行を開始しません。

2026-11-07には右ESC（末尾2326）でPCへの返信が無受信になりました。SWDでCPU動作、PWM停止、UART受信・送信処理を確認しましたが、通信設定の再送・USBリセット・ESC単体リセット・USBだけの抜き差しでは復旧しませんでした。走行電源と両USBを外して5秒待ち、再接続すると両ESCの起動チェックが通りました。根本原因は未特定です。同じ症状では走行プログラムを終了し、完全に電源を切ってから再接続し、まず `uv run hg-cart check --config config.local.json` で確認してください。このチェックは回転指令を送りません。診断記録は `artifacts/hardware/2026-11-07/reconnect/` にあります。

### 操作ログの保存

画面をコピーする代わりに、起動時に `--log` を追加してください。

```bash
# 自動で日時付きファイルを作る
uv run hg-cart drive --config config.local.json --live --log

# 保存先を指定する場合（既存ファイルには上書きしない）
uv run hg-cart drive --config config.local.json --live --log logs/straight-test.jsonl
```

`--log` だけなら `artifacts/diagnostics/drive-日時Z.jsonl` に保存し、起動時と終了時にパスを表示します。日時はUTCです。現在起動中のプログラムはCtrl-Cで終了し、上のコマンドで起動し直してください。症状が出た後にCtrl-Cで終了すれば、保存済みのファイルから調べられます。`--live` を省略した表示専用モードでも記録できます。

JSONL形式（1行につき1レコード）で、次の内容を記録します。

- 起動日時、使用したJSON設定、ゲームパッド情報、左右ESCのUSB固有番号とポート。
- 約50 Hzで保存する操作入力（左右縦軸・十字キー・B・Start）、速度指令、有効／停止状態。入力フレームも別途記録するため短いボタン操作を追えます。
- 左右それぞれの最後に送った速度、応答待ちの速度、ホスト側の始動状態、ESCから受信した状態・要求／推定速度・電流・電圧などの全フィールド。`status_age_s` はそのESC状態を受信してからの経過時間です。ESCの状態は既存の受信値を使い、ログ用の追加UART問い合わせはしません。
- 自動復帰の状態・通知、fault、例外と終了理由。設定や最新状態が取得できる前のエラーでも、起動情報と例外を残します。

`output.*_rpm` は操作から計算した目標値、`wheels.*.last_sent_mrpm` は最後に送った値、`wheels.*.status.est_mrpm` はESCの推定値です。`wheel_sync.*_rpm` は左右の始動待ち・速度差補正後の送信目標、`wheel_sync.reason` はその理由です。`mrpm` はRPMの1000倍、右輪の前進は負符号です。`monotonic_s` で時間を比較でき、絶対時刻の基準は先頭の `session_start.started_at` です。未取得値・非有限値は `null` になります。

ファイルへの書き込みは別スレッドで行い、約0.5秒ごとにバッファを反映します。Ctrl-C・エラー時は両ESCへの停止処理を先に行い、その後に残りのログを保存します。保存が追いつかない場合は一部レコードを省略して警告し、最後の `log_end.dropped_records` に件数を残します。ディスク書き込みに失敗した場合も警告し、走行制御を継続します。強制終了や電源断では末尾が残らない場合があります。`esc_cleanup` は停止送信処理の結果で、実機のPWM停止応答を確認したという意味ではありません。

### タンクモードのコントローラ操作

1. 両スティックを中立にし、十字キーを離して `READY` を確認します。
2. LBは不要です。左右スティックを縦に動かすと、対応する車輪が動きます。
3. 両スティックを中立にし十字キーを離すと制御減速します。すぐにPWMを切るにはBを押します。

| 操作 | 動作（配布JSON：全体上限100 RPM、スティック全倒し30 RPM） |
| --- | --- |
| 左スティック上・下 | 左輪のみ前進・後退。不感帯外を±8〜30 RPMに線形換算 |
| 右スティック上・下 | 右輪のみ前進・後退。不感帯外を±8〜30 RPMに線形換算 |
| 両スティック上／下 | 前進／後退。各輪を独立して速度指定 |
| 左上・右下／左下・右上 | 右／左のその場旋回 |
| スティック横方向・LB | 使用しない |
| 十字キー上・下 | 前進・後退。各輪50％＝50 RPM |
| 十字キー左・右 | 左・右のその場旋回。各輪25％＝25 RPM |
| 十字キー斜め | 両輪にゼロ速度を指定 |
| 両スティック中立・十字キー解放 | 制御減速後にPWM停止。次の指令を受け付ける |
| B | 両輪のPWMを即時停止し、停止状態を保持。電源統合有効時はSSRもOFF |
| 両スティック中立・十字キー解放でStartを押す | Bによる停止保持を解除 |

十字キーを押している間はスティックより優先します。離すと**その時点の両スティック**へ戻ります。十字キーの割合は電流やPWMデューティではなく、`max_speed_rpm` に対する目標回転数の割合です。起動・入力異常後にスティックや十字キーを倒したままでは始動せず、全操作を中立に戻してから操作します。

十字キー操作では、左右両ESCが現在の指令方向で `closed`（速度制御中）になるまで、両輪の指令を最低速度へ下げて保ちます。片側が `ramp` や `blend` のまま、もう片側だけ50 RPMへ加速する動作を防ぎます。両輪の始動後も、遅い側の推定速度に合わせて共通目標を上げ、速い側の指令を補正します。古い状態や逆方向の推定値は始動完了として扱いません。左右スティックは従来どおり独立操作です。センサレス推定を使った速度差の抑制なので、車体の向きやスリップを測って直進を保証する機能ではありません。

十字キーの左右補正後の最終指令にも `acceleration_rpm_s` の変化率制限をかけ、`drive.dpad_smoothing_s`（配布JSONは0.05秒、未指定時0.15秒）で平滑化します。加速の立ち上がりと目標に近づくときの変化を丸め、約10 Hzの推定速度更新で補正指令が跳ねるのを抑えます。この値はフィルタの時定数で、固定の待機時間ではありません。0〜1秒で設定でき、大きくするほど滑らかになりますが追従は遅くなります。0なら平滑化だけを無効にし、最終指令の変化率制限は残ります。JSON編集後の再起動で反映し、ESCの書き換えは不要です。

走行中の非ゼロ目標への減速でも、実速度より低い要求に切り替えた時点で速度PIの加速側積算を破棄します。電圧上限で回転が頭打ちになった後も、以前の加速用電流が減速を遅らせないようにしています。

停止入力は平滑化で遅らせません。中立・十字キー斜めはゼロ速度を直接指令し、B・入力異常はPWM停止します。反転する輪には逆符号の最低速度を渡してESCの制御減速・再始動を開始させ、同じ方向を保つ輪でも、操作による目標速度低下は直ちに送ります。停止付近の始動・反転処理自体はESCが担当します。左右スティックにも各輪独立の加速平滑化を適用します。減速方向の操作では平滑化の蓄積を破棄して低い目標をそのまま送ります。十字キーの自動速度補正は測定の揺れを拾わないよう平滑化を続け、操作による速度低下を優先します。

スティックは `drive.stick_smoothing_s`（配布JSONは0.05秒、未指定時0.15秒、範囲0〜1秒）で加速の滑らかさを調整します。各輪は自身の始動が完了してから最低速度から加速し、他方の始動を待ちません。十字キーとスティックの切り替えでも各輪の加速状態を引き継ぎます。`WAITING_FOR_WHEEL` は操作中の輪の始動待ちです。

画面の `WAITING_FOR_WHEELS` は両輪の始動待ち、`MATCHING_WHEEL_SPEEDS` は共通目標の加速・速度差補正中です。片側の始動が完了しない場合は最低速度まで下げた状態で待ち、ESCの始動タイムアウト時は既存の両輪停止・自動復帰へ移ります。

100 RPMは**指定できる目標値の上限**で、到達速度を保証しません。25.2 V・既存モーター定数の独立モデルでは、100 RPM指令でも電圧制限で約32.5 RPMに留まります。実機の100 RPM到達や接地負荷は未確認です。2 Aの電流上限・電圧制限・過速度監視は維持します。

`observer_lock` はセンサレスの回転推定を確立・維持できなかった異常です。この異常では操作プログラムを終了せず、両輪のPWMを切り、2.5秒待ってから自動復帰します。再始動時には**その時点のスティック／十字キー指令**を使います。待機中も入力を読み続け、両スティック中立・十字キー解放、またはBで再始動を取り消します。中立なら停止したままです。推定を取り直す始動時間も必要なので、車輪が一瞬も止まらず動き続ける機能ではありません。

故障直後に `ERR rpm requires active runrpm; ... fault=observer_lock` が返っても、自動復帰を処理します。詳細な故障フレームが別のUSB読み取りで届く場合は、もう片輪を停止し、最大250 msだけ確認を待ちます。PWM停止済みの故障を確認できない場合や、別の異常があれば停止して終了します。

画面には `RECOVERING` と残り時間を表示します。自動再試行は連続3回までで、失敗が続けば `RECOVERY_LIMIT` で再操作待ちになります。プログラムを起動し直す必要はなく、両スティック中立・十字キー解放から再操作できます。両輪が閉ループで10秒間正常に動けば再試行回数をリセットします。過電流・電圧異常・通信断などは自動復帰の対象外です。

異常時とその直前のESC状態、左右、USB固有番号を `artifacts/diagnostics/esc-faults.jsonl` に追記します。これにより、停止でESCの異常状態が消えても原因調査用の情報が残ります。

`invalid_sample` の詳細は `sample_reason` に記録し、Pythonのエラーにも表示します。3相電流の合計の監視は、絶対値1.2 A超が10回連続（20 kHzで0.5 ms）した場合、または2 Aを超えた場合に停止します。2 A超と非数値は即停止です。この値は測定値の整合性の許容値で、モーターへ流す電流の上限ではありません。各輪のIq上限2 A、相電流トリップ4 A、ADC異常・電圧・温度・通信の保護は維持しています。

始動時の同期確認は、良好な推定を1加点、不良な推定を5減点する方式です。速度・角度の条件を外れたら得点をゼロに戻し、2000点かつその時点の推定も良好なときだけ閉ループへの移行を開始します。短いノイズ1回で100 msの確認をやり直す従来方式を改善し、継続的に推定が悪い場合の6秒タイムアウトと運転中の同期喪失保護は残しています。

速度制御中の過速度監視には、速度PIでも使用している時定数30 msの平滑化済み推定値を使い、内部の要求速度とランプ目標の大きい方に対して、配布JSONでは2倍を超えると停止します（`esc.overspeed_filtered_ratio`、未指定時1.5倍）。瞬時推定値が3倍を超えた場合は即停止します。低速・無負荷で瞬時推定だけが跳ねる誤停止を抑えつつ、継続的な過速度と大きな異常値は検出します。電流指令など従来のベンチモードは瞬時推定1.5倍の制限を維持します。`observer_reason` で始動同期失敗、同期喪失、過速度の内訳を記録します。

**LB操作は不要です。** 操作中の反転はESCが `decelerate` → `settle` → `align` → `ramp` → `blend` → `closed` と処理し、ホストの固定2.5秒待機は入りません。内輪だけの反転で外輪を止めず、途中で変えた目標も最新値を使います。Bを押すとPWMを即時停止し、保留中の再始動を取り消します。

ホールなしのセンサレス制御です。減速時は最大 `min(0.6 A, 電流上限)` の逆向きIqを使い、低速になった後は300 msの相短絡で減速してから再始動します。停止位置や完全な静止を外部センサーで測っているわけではありません。ゼロ速度を跨ぐ完全な連続FOCではなく、反転時には推定を取り直す始動時間が残ります。

B・入力異常などでPWMを切った後、中立確認を経て逆方向へ始動するときは、従来どおり停止待機があります。その場合だけ `DIRECTION_CHANGE_WAIT` と残り時間を表示します。

スティックの不感帯（±0.12）の外を、`min_speed_rpm` から `stick_max_speed_rpm` まで直線的に割り当てます。配布JSONは8〜30 RPMです。傾き20％→10 RPM、40％→15 RPM、56％→19 RPM、100％→30 RPMとなり、後退側も同じ比率です。`stick_max_speed_rpm` は8〜`max_speed_rpm`、未指定／nullなら全体上限を使います。`max_speed_rpm=100` と十字キーの50％／25％は維持しています。

2026-11-05の `drive-20261105T123036.688520Z.jsonl` では、ホストの加速指令は20 RPM/s以内でしたが、推定速度は約30 RPMで頭打ちでした。以前の換算では傾き約38％で30 RPMを要求し、その先の操作が実速度に反映されにくくなっていました。今回の30 RPM設定はこの無負荷ログに合わせた操作範囲で、接地負荷・電池電圧によって到達速度は変わります。

**0〜8 RPMを連続指定することはできません。** 中立は0 RPMで、始動中は8 RPMに向けて推定を確立します。ログでは左の始動に約1.6〜1.9秒、右はそれ以上かかる場合があり、右の `startup_lock` 失敗も2回ありました。線形換算・加速FFだけでこの待機や失敗が解消するとは限りません。十字キーで計算値が8 RPM未満なら8 RPMへ切り上げます。加速指令は `acceleration_rpm_s`（配布JSONは30 RPM/s）以内で平滑化し、減速・中立はすぐ送信します。

画面の `stick L/R` は各縦軸（上が正）、`Dpad X/Y` は右／上が正です。`RPM_cmd` は操作から求めた符号付き目標値、`RPM_send` は加速平滑化・始動待ち・十字キーの速度差補正後の送信目標、括弧内のRPMはセンサレス推定速度です。右モーターは前進時に負符号なので、配布JSONのスティック前進最大操作で `L=+30 / R=-30` と表示されます。

加速FFはESC内部の速度目標の上昇率に比例して電流を加え、速度誤差が出る前から駆動力を補います。`esc.acceleration_ff_a=0.3` は設定加速度（配布JSONは30 RPM/s）で最大0.3 A、半分の加速度なら約0.15 Aです。UART指令の段差を30 msのフィルターで丸め、減速指令・制御停止では即座にFFをゼロにします。PIとFFの合計を2 A以内に制限し、制動側0.6 Aの上限も維持します。定常走行中はFFがゼロへ戻り、負荷の補正はPIが担当します。始動・推定確立の判定を省略する機能ではありません。

`esc.startup_current_a` と `esc.acceleration_ff_a` は起動時にJSONから転送します。左右別に調整する場合は `left_esc`／`right_esc` に同じキーを指定します。ログの `ff_mA` は加速FFの現在値（モーター内部の駆動方向を正）です。この追加には設定プロトコル2のESCファームウェアが必要で、旧版は始動前に拒否します。

### 起動時にESCへ送る設定

`drive --live` と `check` は、まず両輪を停止し、共通の `esc` に左右の `left_esc` / `right_esc` を上書きした設定を送ります。全19項目を一時領域へ転送し、ESCが範囲と組み合わせを検証して一括反映します。Pythonは全項目を読み戻して一致を確認し、その後にR/Lの設定・照合を行います。転送失敗、未対応ファームウェア、不一致、設定値の範囲外では両輪を停止して終了します。ESCがリセットされたり設定が失われたりした場合も走行を止め、再起動時に再設定します。

値はESCのRAMに保持し、起動ごとのFlash書き込みはしません。**今回一度ファームウェアを更新した後は、JSONを編集して同じコマンドで起動し直せば反映されます。** 運転中にJSONを編集してもその場では反映しません。`drive` の最低/最高速度・Iq上限・加速度も同時にESC側の上限へ反映するため、設定を二重に管理する必要はありません。R/Lは従来の `left_motor` / `right_motor`、前進符号は `drive.left_sign` / `right_sign` です。

## 停止処理

- 起動時に両ESCのPWMを停止し、温度変化による電流センサーのずれを減らすためゼロ点を再校正します。通信仕様・電源・モーター定数を検証してから操作を受け付けます。
- 有線F310ではスティックを固定して操作できます。主ループが入力デバイスを確認し、USB読み取り失敗・古い入力キュー・キューあふれでは両輪停止後に終了します。USBデバイス確認は、同じ入力値のまま故障したコントローラの検出を保証するものではありません。
- F710は受信機だけ残る無線断を考慮し、入力イベントが0.5秒変化しなければ停止します。F710ではスティック固定でも停止します。
- 片輪のfault、目標速度の応答不一致・タイムアウト、状態ログ停止、ホスト制御ループ遅延では両輪を停止します。`observer_lock` だけはPWM停止・校正完了を確認して上記の自動復帰を行い、再始動前に新しい状態ログで電源・通信仕様・モーター定数を照合します。他のfault、通信異常、ESC再起動では自動再始動しません。
- `ping` は主制御ループだけから送信します。ホスト停止時にはESCの500 ms通信監視でPWMを停止します。独立watchdogも維持しています。
- 速度制御の連続運転は、明示的なUART `runrpm` だけで許可しています。他の既存ベンチ運転の10秒制限、始動タイムアウト、過電流・電圧・センサレス推定喪失・過速度等の保護は維持します。
- 操作中の速度超過・減速時には最大0.6 Aの制動Iqを使います。電圧保護は18〜26 Vです。坂道での停止保持は実装していません。

| UARTコマンド | 動作 |
| --- | --- |
| `cartcap` | `cart_protocol=4 config_protocol=2 supported_max_mrpm=100000 brake_from_feedback=1 acceleration_ff=1`、速度・電流範囲、監視時間を返す |
| `cartcfg` | 適用済み19項目、設定ID、転送途中かどうかを返す |
| `cfgbegin ID` → `cfgset KEY INTEGER` ×19 → `cfgapply ID` | PWM停止・idle時だけ全設定を一括反映。値はmV・mA・mRPMなどの整数単位。通常はPythonが送信 |
| `zero` | PWM停止中の電流ゼロ点校正。`calibration=started`、完了は `status` の `cal=ok` |
| `arm` → `runrpm 10 2 20` | 正方向10 RPM、Iq上限2 A、目標変化率20 RPM/sで始動 |
| `arm` → `runrpm -10 2 20` | 逆方向10 RPM、Iq上限2 A、目標変化率20 RPM/sで始動 |
| `rpm -8` | 逆方向の始動中・閉ループ運転中に目標を-8 RPMへ変更 |
| `rpm 0` | 制御減速後にPWM停止して `ready` へ。次の非ゼロ指令で再始動 |
| `stop` / Ctrl-C文字 | 即時PWM停止、保留指令を破棄 |
| `ping` | 500 ms監視を更新。速度指令の送信だけでは代用しない |
| `status` | 状態・fault・PWM・方向・要求/推定RPM・電流上限を返す |

始動時は8 RPMへ向けてセンサレス推定を確立し、その後に最新の目標速度へ移行します。Pythonは始動中も目標変更を送り、同じ方向の変更で始動手順をやり直しません。入力の読み取りと応答確認は約200 Hz（5 ms周期）、目標変更は最大100 Hzで送信し、未確認の指令は1件までに制限します。応答待ちの間に変わった古い目標をキューへ蓄積せず、次の送信では最新値を使います。運転中の周期ログを短縮し、指令応答のUART待ちを減らしています。`status` とfault発生時には詳細状態を返します。`runrpm` の加速度引数を省略した場合は起動時に転送した `max_slew_mrpm_s` の値です（リセット直後の既定値は20 RPM/s）。運転中の反対符号の `rpm` は、制御減速後にその方向へ再始動します。従来の `runiq` / `iq` は診断用に残していますが、Pythonの走行モードでは使いません。旧ファームウェアのままでは始動を拒否します。

RPM換算は既存プロジェクトの車輪1回転あたり199電気周期を使用します。表示値はセンサレス推定で、外部エンコーダの測定値ではありません。
